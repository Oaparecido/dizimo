1. Contexto inicial

A aplicação é um projeto Laravel 13 com Inertia.js + Vue 3 + Tailwind CSS 4. O objetivo era prepará-la para deploy no Render, uma plataforma de cloud que aceita containers Docker ou build nativo.

Durante o processo, encontramos três problemas que impediam o deploy e a CI de passarem:

  1. CI do GitHub Actions quebravam no PHP 8.3 porque as dependências travadas no composer.lock exigiam PHP ≥8.4.
  2. Render rejeitava o render.yaml porque usava fromService com tipo inválido (psv) e propriedades não suportadas (database, user, password).
  3. Dockerfile vazio — nenhuma instrução de build existia.

3. Problema #1 — CI quebra no PHP 8.3

Erro no GitHub Actions
Your lock file does not contain a compatible set of packages. Please run composer update.

Problem 1
  - symfony/clock v8.1.0 requires php >=8.4.1 → your php version (8.3.31) does not satisfy that requirement.
Problem 2
  - symfony/console v8.1.1 requires php >=8.4.1 → your php version (8.3.31) does not satisfy that requirement.
…
19 problemas no total, todos Symfony + Laravel exigindo PHP ≥8.4

Causa

O composer.lock foi gerado com PHP 8.5 (versão local do desenvolvedor). As versões mais recentes do Symfony (8.1.x) — que o Laravel 13 traz como dependência — exigem PHP ≥8.4.1. O composer.json ainda declarava "php": "^8.3", mas o lock file já tinha pacotes incompatíveis com 8.3.

A CI (.github/workflows/tests.yml) usava um matrix com PHP ['8.3', '8.4', '8.5']. Ao rodar composer install no runner PHP 8.3, o Composer validava o lock file contra a plataforma e rejeitava: 

Composer install (PHP 8.3)
  → Lê composer.lock
  → Vê symfony/console v8.1.1 (requer php >=8.4.1)
  → Vê php version 8.3.31
  → Erro: "Your lock file does not contain a compatible set of packages"

Solução

Duas alterações foram necessárias:

1. composer.json — atualizar requiremento PHP
// Antes
"php": "^8.3",

// Depois
"php": "^8.4",

Isso declara que a aplicação precisa de PHP 8.4+. O composer.lock não precisou ser alterado porque os pacotes já eram compatíveis com 8.4 — só o requiremento do composer.json que estava errado.

2. tests.yml — remover PHP 8.3 do matrix + --ignore-platform-reqs
# Antes
php-version: ['8.3', '8.4', '8.5']
composer install --no-interaction --prefer-dist --optimize-autoloader

# Depois
php-version: ['8.4', '8.5']
composer install --no-interaction --prefer-dist --optimize-autoloader --ignore-platform-reqs

Por que --ignore-platform-reqs?

O Composer, por padrão, valida se a plataforma atual (PHP + extensões) satisfaz todas as dependências do lock file. Em ambientes de CI/Docker, o ambiente de build pode ter extensões ligeiramente diferentes do ambiente de produção. Adicionar essa flag elimina falsos positivos sem risco: o lock file já foi verificado localmente e as extensões corretas estarão na imagem Docker final.

4. Problema #2 — Render rejeita render.yaml

Erro no Render
services[0].envVars[4].fromService.type
  psv not a valid type

services[0].envVars[6].fromService.property
  invalid service property: database. Valid properties are connectionString, host, hostport, port.

services[0].envVars[7].fromService.property
  invalid service property: user. Valid properties are connectionString, host, hostport, port.

services[0].envVars[8].fromService.property
  invalid service property: password. Valid properties are connectionString, host, hostport, port.

Causa

O render.yaml original tentava referenciar o banco de dados PostgreSQL usando fromService com type: psv. Esse tipo não existe no Render Blueprint. Além disso, as propriedades database, user e password não são válidas em fromService — apenas host, port, hostport e connectionString.

Solução

O Render Blueprint tem uma sintaxe específica para bancos de dados: fromDatabase.

render.yaml — usar fromDatabase com connectionString
# Antes (ERRADO)
- key: DB_HOST
  fromService:
    name: dizimo-db
    type: psv          # ← tipo inválido
    property: host
- key: DB_DATABASE
  fromService:
    name: dizimo-db
    type: psv
    property: database # ← propriedade inválida
- key: DB_USERNAME
  fromService:
    name: dizimo-db
    type: psv
    property: user     # ← propriedade inválida
- key: DB_PASSWORD
  fromService:
    name: dizimo-db
    type: psv
    property: password # ← propriedade inválida

# Depois (CERTO) — uma única variável com a connection string completa
- key: DB_URL
  fromDatabase:           # ← palavra-chave correta para bancos
    name: dizimo-db
    property: connectionString  # ← retorna "postgresql://user:pass@host:5432/db"

Por que isso funciona?

O Render injeta internamente a connection string completa do PostgreSQL: postgresql://dizimo:senha@dizimo-db.render-internal.com:5432/dizimo. O Laravel config/database.php já lê a variável DB_URL na seção pgsql: 

'pgsql' => [
    'driver' => 'pgsql',
    'url' => env('DB_URL'),  // ← Laravel parseia a connection string automaticamente
    'host' => env('DB_HOST', '127.0.0.1'),
    'port' => env('DB_PORT', '5432'),
    'database' => env('DB_DATABASE', 'laravel'),
    'username' => env('DB_USERNAME', 'root'),
    'password' => env('DB_PASSWORD', ''),
],

Quando DB_URL está presente, o Laravel extrai host, porta, database, usuário e senha diretamente da string — eliminando a necessidade de declarar variáveis individuais.

Saiba mais: fromDatabase vs fromService

No Render Blueprint:

  • fromDatabase → para referenciar bancos de dados gerenciados (PostgreSQL, Redis). Propriedades: connectionString, host, port, user, password, database.
  • fromService → para referenciar outros serviços (web, worker, private service). Tipos válidos: web, pserv, worker, cron, static. Propriedades: host, port, hostport, connectionString.

APP_URL via RENDER_EXTERNAL_URL

Também adicionamos no start.sh a detecção automática da URL pública: 

# No start.sh
if [ -n "$RENDER_EXTERNAL_URL" ]; then
    export APP_URL="$RENDER_EXTERNAL_URL"
fi

O Render injeta a variável de ambiente RENDER_EXTERNAL_URL com a URL pública do serviço (ex: https://dizimo.onrender.com). O start.sh converte isso em APP_URL para o Laravel gerar links corretamente.

5. Problema #3 — Dockerfile vazio

O Dockerfile foi criado do zero seguindo o padrão multi-stage, que divide o build em estágios independentes para gerar uma imagem final enxuta.

Estrutura do Dockerfile

# ──────────────────────────────────────────
# ESTÁGIO 1: Build dos assets (Node.js)
# ──────────────────────────────────────────
FROM node:22-alpine AS build-assets
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                    # Instala dependências Node de forma determinística
COPY . .
RUN npm run build             # Gera os arquivos em public/build

# ──────────────────────────────────────────
# ESTÁGIO 2: Instalação das dependências PHP (Composer)
# ──────────────────────────────────────────
FROM composer:2 AS build-vendor
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --optimize-autoloader --no-interaction --ignore-platform-reqs

# ──────────────────────────────────────────
# ESTÁGIO 3: Imagem final (PHP + runtime)
# ──────────────────────────────────────────
FROM php:8.4-cli-alpine AS final
WORKDIR /app

# Instala extensões PHP necessárias
RUN apk add --no-cache \
    postgresql-dev libzip-dev unzip \
    && docker-php-ext-install \
    pdo pdo_pgsql pdo_sqlite zip bcmath opcache

# Copia artefatos dos estágios anteriores
COPY --from=build-assets --chown=www-data:www-data /app/public/build /app/public/build
COPY --from=build-vendor --chown=www-data:www-data /app/vendor /app/vendor

# Copia o código-fonte e configura permissões
COPY --chown=www-data:www-data . .
RUN chmod -R 775 storage bootstrap/cache

# Script de inicialização
COPY start.sh /start.sh
RUN chmod +x /start.sh

# Permite requisições concorrentes no servidor embutido
ENV PHP_CLI_SERVER_WORKERS=4

EXPOSE 10000
CMD ["/start.sh"]

Pontos importantes do Dockerfile

ItemExplicação
Multi-stage 3 estágios separados: cada um instala apenas o necessário. O Node e o Composer NÃO vão para a imagem final — só os artefatos compilados.
--chown=www-data:www-data O usuário www-data existe na imagem php:8.4-cli-alpine. Todos os arquivos são copiados com esse dono para evitar problemas de permissão.
chmod -R 775 storage bootstrap/cache O Laravel precisa escrever logs, cache, sessions, views compiladas nesses diretórios.
PHP_CLI_SERVER_WORKERS=4 php artisan serve usa o servidor embutido do PHP, que é single-thread por padrão. Essa env var permite 4 workers concorrentes.
EXPOSE 10000 O Render define a variável PORT (padrão 10000). O container escuta em 0.0.0.0:$PORT.

6. Script de inicialização (start.sh)

#!/bin/sh
set -e  # Para o script se qualquer comando falhar

# Se estiver no Render, usa a URL pública fornecida pela plataforma
if [ -n "$RENDER_EXTERNAL_URL" ]; then
    export APP_URL="$RENDER_EXTERNAL_URL"
fi

# Gera APP_KEY se não estiver definida (Render pode injetar via generateValue)
if [ -z "$APP_KEY" ] || [ "$APP_KEY" = "base64:" ]; then
    php artisan key:generate --force
fi

# Cria o symlink public/storage → storage/app/public
php artisan storage:link --force 2>/dev/null || true

# Roda migrations (força execução em produção)
php artisan migrate --force

# Em produção, faz cache de config, rotas, views e eventos
if [ "$APP_ENV" = "production" ]; then
    php artisan config:cache
    php artisan route:cache
    php artisan view:cache
    php artisan event:cache
fi

# Inicia o servidor — PORT é definido pelo Render (padrão 10000)
exec php artisan serve --host=0.0.0.0 --port=${PORT:-10000}
ComandoFunção
php artisan key:generateGera uma APP_KEY de 32 caracteres (AES-256-CBC) se não existir. Necessário para criptografia de sessões, cookies, etc.
php artisan storage:linkCria o link simbólico de public/storage para storage/app/public, permitindo acesso público a uploads.
php artisan migrateExecuta as migrations pendentes. A flag --force é necessária em produção para suprimir a confirmação.
config:cache / route:cache / view:cache / event:cacheCompila e armazena em cache todos os arquivos de configuração, rotas, views e eventos. Aumenta a performance em produção pois evita leitura/interpretação de arquivos a cada requisição.
php artisan serve --host=0.0.0.0Inicia o servidor HTTP embutido do PHP. 0.0.0.0 é obrigatório no Render para aceitar conexões externas.
Nota sobre o servidor embutido

php artisan serve usa o servidor de desenvolvimento do PHP, que não é recomendado para produção com alto tráfego. Porém, para aplicações de baixo volume no Render, ele funciona bem — especialmente com PHP_CLI_SERVER_WORKERS=4. Para escala maior, o próximo passo seria usar FrankenPHP ou Nginx + PHP-FPM.

7. .dockerignore

O .dockerignore diz ao Docker quais arquivos não enviar para o daemon durante o build. Isso acelera o build e evita que dados desnecessários entrem na imagem.

9. Fluxo completo do deploy

Quando o desenvolvedor faz push para o repositório:

  1. GitHub Actions (CI) — Roda o workflow tests.yml:
    • PHP 8.4 e 8.5 (matrix)
    • composer install --ignore-platform-reqs
    • npm run build (assets)
    • composer types:check (PHPStan)
    • php artisan test (Pest)
  2. Render detecta o push — Inicia o deploy:
    • Lê o render.yaml
    • Cria/cria o banco PostgreSQL (dizimo-db)
    • Faz o build da imagem Docker via Dockerfile
    • Injeta as env vars: DB_URL (connection string), APP_KEY (gerada), etc.
    • Inicia o container com start.sh
    • Health check na rota /up
  3. Container inicia — start.sh:
    • Detecta RENDER_EXTERNAL_URL → define APP_URL
    • Gera APP_KEY se necessário
    • Cria symlink de storage
    • Roda migrate --force
    • Cacheia config, rotas, views, eventos
    • Inicia php artisan serve na porta $PORT

10. Sobre o composer.lock e --ignore-platform-reqs

Por que usamos --ignore-platform-reqs no Dockerfile?

O estágio build-vendor usa a imagem composer:2, que tem uma versão do PHP e um conjunto de extensões diferente da imagem final (php:8.4-cli-alpine). O Composer por padrão valida se a plataforma atual atende aos requirements do lock file — e como o composer:2 tem PHP 8.3 enquanto o lock pede ≥8.4, a validação falharia.

A solução --ignore-platform-reqs diz: "apenas instale os pacotes, não valide a plataforma". É seguro porque:

  • O lock file já foi verificado localmente com PHP 8.5
  • A imagem final (php:8.4-cli-alpine) tem todas as extensões necessárias
  • O runtime da aplicação é php:8.4-cli-alpine, não composer:2

E no CI do GitHub Actions?

O mesmo princípio se aplica. O runner do GitHub Actions tem PHP 8.4/8.5 com extensões que podem diferir do ambiente local. --ignore-platform-reqs previne quebras por diferenças de extensões ou versões de patch, mantendo a CI estável.

⚠️ Recomendação

--ignore-platform-reqs é seguro aqui porque o lock file já está consolidado e o ambiente de produção é controlado (Docker). Em projetos onde o ambiente de produção pode variar, prefira usar --ignore-platform-req=php (que só ignora a versão do PHP, mas ainda valida extensões) ou instalar as extensões faltantes no ambiente de build.
